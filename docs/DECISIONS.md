# Design decisions

This log records judgement calls made while building the toolkit, so that reviewers can
challenge them explicitly. Regulatory *interpretations* (as opposed to engineering choices)
live in [`ASSUMPTIONS.md`](ASSUMPTIONS.md).

| ID | Decision | Rationale |
|----|----------|-----------|
| D-001 | Package `dora_roi` (src layout), CLI entry point `roi`, Python ≥ 3.11. | `StrEnum`, `Self` and modern typing; 3.11 is the oldest CPython still widely deployed in banks' managed environments. |
| D-002 | **All model fields are `Optional` at the type level.** Mandatory / conditional / optional requirements are declared as metadata (`Col(requirement=…)`) and enforced by the validation engine. | A register under construction is always incomplete. If Pydantic enforced mandatoriness, a single missing value would make the whole row unloadable and hide every other problem. Consultants need *all* findings in one run. |
| D-003 | Format checks (LEI checksum, ISO 3166 / ISO 4217 codes, ISO 8601 dates, code lists, ranges) are enforced by Pydantic annotated types raising `PydanticCustomError("roi_*")`. The parser maps these error types onto validation rule IDs (`FLD-*`). Invalid values are reported and then *discarded* (set to `None`) so the rest of the row still loads. | One source of truth for formats (usable programmatically: `ContractSpecific.model_validate(...)`), while still giving the validation engine full control over severities and reporting. The discarded attributes are tracked (`record.invalid_fields`) so that the mandatory-field rule does not double-report them. |
| D-004 | Column metadata is attached with `typing.Annotated[..., Col(...)]` on the model fields rather than in a separate schema file. | Keeps the typed model, the Excel template generator, the importers, the exporter and the documentation in sync from a single declaration. |
| D-005 | Code lists use **toolkit-internal stable codes** (e.g. `S19`, `CRITICAL`, `OVERARCHING`) with human labels; importers accept code, label, alias or an `eba_XX:` prefixed value case-insensitively. | The exact EBA taxonomy member names for many enumerations could not be verified offline (see A-CL-*). Internal codes decouple the data model from taxonomy releases; the xBRL-CSV exporter applies a configurable mapping. |
| D-006 | Reference data (249 ISO 3166-1 countries, ISO 4217 currencies, EU/EEA lists) is embedded, not pulled from `pycountry`. | Zero heavyweight dependencies, deterministic behaviour, easy to audit. |
| D-007 | Primary key of B_05.01 is the provider identification code alone (not code + code type). | LEI and EUID namespaces do not overlap syntactically; using the code alone makes cross-template look-ups simpler and catches the same provider being reported twice with different code types. |
| D-008 | Primary key of B_06.01 is (function identifier, entity LEI). | In a group register the same function identifier may legitimately be reused by different entities; B_02.02 carries both values so the composite key can be resolved. |
| D-009 | All importers produce a common untyped `RawRegister` (column code → raw cell value + source row number), which a single parser turns into the typed model. | Excel, CSV and xBRL-CSV get identical semantics, error messages and row references for free. |
| D-010 | Generated workbooks have one sheet per template named by its code, row 1 = column codes, row 2 = labels, row 3 = requirement/format hint, data from row 4, plus hidden code-list sheet for drop-downs. The importer finds the header in the first 10 rows, accepts codes *or* labels, and skips the generated label/hint rows. | Robust to clients who add title rows or rename headers to labels, while keeping a machine-readable header for round-tripping. |
| D-011 | Import problems (unknown sheet, missing template, unknown column, no header) are findings (`IMP-*`), not exceptions. Only unreadable inputs (missing path, unsupported format) raise. | A consultant should get one report listing *everything* wrong with a client's file. |
| D-012 | The xBRL-CSV exporter writes the package even if validation fails; the CLI warns and `--strict` refuses. Enumerations default to internal codes plus an explicit warning rather than invented taxonomy member IDs. | Producing a plausible-looking but wrong taxonomy code would be worse than an obviously unmapped one. |
| D-013 | The xBRL-CSV reader is the inverse of the exporter (strips `eba_GA:`/`eba_CU:` prefixes, inverts the code map, honours filing indicators). | Enables round-trip tests and re-validation of a package before upload. |
| D-014 | CSV import auto-detects `,` `;` and tab delimiters and strips a UTF-8 BOM. | Excel on European locales exports semicolon-separated CSV with BOM by default. |
| D-015 | Charts are generated as inline SVG/HTML by a ~150-line module instead of using matplotlib/plotly. | Self-contained single-file HTML a client can e-mail or print, no JS/CDN dependency, light/dark aware, deterministic output for tests. |
| D-016 | Chart design: single-hue ranked bars with value labels at the tip, part-to-whole as a segmented bar with legend values, an ordinal blue ramp for substitutability, status colours only for severity – each paired with a text label, a table view for every chart, and palettes checked for colour-vision deficiency in light and dark mode. | A CRO deck is printed and photocopied; identity must never depend on colour alone. |
| D-017 | Geography is reported both for the contracting provider and for its ultimate parent group; the third-country key message uses the group view. | An Irish subsidiary of a US hyperscaler is contractually "EU" but carries third-country group risk – the more relevant view for concentration. |
| D-018 | The CLI uses `click` (already a dependency of the web stack) with exit codes 0 = ok, 1 = findings at/above `--fail-on`, 2 = usage/input error. | Script/CI friendly. |
| D-019 | `docs/REGULATORY_MAPPING.md` and `docs/DATA_DICTIONARY.md` are generated from the code (`python -m dora_roi.docs`) and a test fails if they are stale. | Documentation that cannot drift from the rules. |
| D-020 | Sample organisations are entirely fictional (including the hyperscalers "Nimbus", "Stratus", "Cirrus"), with checksum-valid synthetic LEIs derived from a hash of the name. | Attaching fabricated identifiers and contract data to real company names would be misleading in a public repository; the US-parent/EU-subsidiary pattern of real hyperscalers is reproduced structurally instead. |
| D-021 | The sample generator returns both the "as filed" register (`source_register`, which may hold deliberately invalid raw strings such as `UK` or `31/12/2027`) and the register after a round-trip through the parser. Injected errors are listed with the rule IDs expected to catch them and a test asserts each is detected. | Format errors can only exist in a file, not in a validated model; the manifest turns the sample into a regression test of the validator. |
| D-022 | Sample reference date is 31 December 2025 and the maintaining entity is the German EU intermediate parent; the Swiss holding is outside the scope and only appears as parent LEI (one expected `XRF-014` info). | Mirrors a Swiss group whose EU sub-group reports under DORA. |
| D-023 | Web UI: FastAPI with server-rendered Jinja2 pages (no SPA, no build step), reusing the report templates and charts; analyses held in a bounded in-memory LRU store; uploads limited to 25 MB and `.xlsx`/`.zip`, parsed from a temporary file that is deleted immediately. | Registers contain commercially sensitive contract data: nothing is persisted, and the app is intended for local/single-team use behind the organisation's own authentication. |
| D-024 | Web UI stays **server-rendered (FastAPI + Jinja2) with ~150 lines of vanilla JavaScript** for progressive enhancement – no SPA framework. | Every screen is forms and tables; server rendering gives accessible HTML by default, works without JS (bank desktops often restrict scripts), needs no build toolchain and keeps the Docker image small. JS only adds in-place saving, graph highlighting and the theme switch. |
| D-025 | A **workspace** keeps the *raw* cell values as the source of truth and re-derives the typed register, validation report and analysis after each change (~90 ms for the 1 000-row sample). Every change creates a version (max. 50, the import is kept). | Invalid values must stay visible and editable; full re-validation is fast enough that incremental validation would add complexity for no benefit; versions enable "compare with an earlier version". |
| D-026 | **Data-quality score** = average over records of 1 (no finding), 0.5 (warnings only), 0 (any error), × 100, capped at 50 when a register-level error exists. Readiness is separate: *ready* only with zero errors, *almost* with ≤ 10. | Easy to explain to a client ("97 % of records are clean") while never suggesting that a register with errors is submittable. |
| D-027 | Fix suggestions are deterministic normalisations (ISO codes from names/aliases, day-first date parsing, closest code-list value, LEI case/spacing, recomputed LEI check digits). Low-confidence suggestions are labelled "check before applying"; nothing is changed without the user pressing Save. Bulk fix applies the same value to all rows sharing rule, column and wrong value (or the same empty mandatory column). | Consultants fix dozens of identical errors at once, but compliance data must never be silently rewritten. |
| D-028 | **Column-mapping import** maps a contract-centric inventory (one row per contract/service) to 17 RoI fields using EN/DE synonyms, fuzzy header matching and value patterns (LEIs, dates, currencies); each target field can be used once. Missing information (e.g. LEIs) becomes placeholders (`TBD-…`) or empty mandatory cells that the Fix step then reports. | This is how client data actually arrives; producing a draft register that the validator can guide to completion beats rejecting the file. |
| D-029 | The dependency graph uses a deterministic layered (longest-path + barycentre) layout computed in Python and rendered as SVG with focusable links; colour by *criticality* (emphasis: critical vs grey) or by *region* (fixed categorical slots, validated for CVD). A table of chains is the text alternative. | No graph library, stable layout across reloads and screenshots, keyboard and screen-reader access. |
| D-030 | **i18n**: interface strings, rule titles and plain-language explanations exist in English and German (tests assert both catalogues have the same keys and every rule is explained). Per-finding validator messages remain English. | Messages embed technical values and ITS labels; translating them would require message templates for 62 rules – a sensible next step, not a blocker. |
| D-031 | **Accessibility** is tested automatically: Playwright end-to-end tests run axe-core 4.10 (WCAG 2.0/2.1/2.2 A + AA rules) on every main screen in light and dark mode, plus keyboard (skip link, focus), reflow at 360 px and no-JS-reload checks. | Automated checks catch ~30–50 % of WCAG issues; manual review with a screen reader remains recommended (see `docs/UX.md`). |
| D-032 | README screenshots are generated by `scripts/make_screenshots.py` against the sample data, at device scale factor 2. | Screenshots never drift from the UI. |
| D-033 | Docker: two-stage build on `python:3.12-slim` (wheels built in stage 1), non-root user, health check; compose publishes on **127.0.0.1 only**, read-only root filesystem, `tmpfs` for `/tmp`, all capabilities dropped, `no-new-privileges`. An optional `ca_bundle` build secret supports TLS-inspecting corporate proxies. CI builds the image and smoke-tests it with the same hardening. | Consultants run it on client laptops: one command, nothing listening on the network, nothing persisted, works behind bank proxies. |
| D-034 | Part A (reconciliation with official EBA sources) was **not** carried out from memory: `reference/eba/` was absent and EBA/EUR-Lex were unreachable from the build environment. Instead, `roi check-package` compares our package with any reference package (layout, metadata, parameters, filing indicators, headers, value styles) so that step 4 of the reconciliation is a single command once the official sample is present. | Presenting remembered template codes or check IDs as "official" would defeat the purpose of the reconciliation. |
| D-035 | Exported workbooks store every text value as a literal string (`data_type='s'`, quote prefix for `= + - @`); machine-oriented CSV/xBRL-CSV files are **not** altered (prefixing would corrupt data), but the human-oriented audit-log CSV is neutralised. | Prevents spreadsheet formula injection from client-supplied data without changing regulatory values. |
| D-036 | Only warnings and info findings can be *accepted* with a justification; errors cannot. Accepted findings are kept in the report (`accepted`) and the audit trail. | An accepted error would still be rejected by the supervisor; acceptance is for legitimate exceptions such as an out-of-scope parent. |
| D-037 | Versions are positions in the append-only change log; earlier states are rebuilt by undoing changes. | O(1) memory per edit instead of a full copy; the change log doubles as the audit trail. |
| D-038 | Failure impact counts a function as affected when the provider is its direct provider **or** appears at rank ≥ 2 in the supply chain of an arrangement supporting it; the "≥ N critical functions" key message uses this inclusive count and shows the direct count alongside. | The question a Head of Third-Party Risk asks is "what breaks if this provider fails", which subcontracting answers more often than direct contracts. |
| D-039 | Web isolation boundary = a random **browser session** (HttpOnly, SameSite=Strict cookie, 256-bit token); workspaces and wizards are owned by the session that created them and are invisible (404) to others. No user accounts. | Delivers isolation on shared deployments without introducing authentication, which belongs to the reverse proxy / SSO in front of the app. |
| D-040 | Notice deadline = earliest (end date − entity notice period) across an arrangement's B_02.02 rows; indefinite (9999-12-31) and already-ended arrangements are excluded. | Matches how procurement and third-party-risk teams plan exits and renegotiations. |
| D-041 | Security scanning in CI: `bandit` (fail on medium+ severity and confidence) over `src/`, and `pip-audit` against a frozen list of the runtime + web dependencies installed in an isolated venv. The four `Markup` constructions flagged by bandit carry `# nosec B704` with a justification and are covered by XSS payload tests. | Auditing only what ships avoids false alarms from CI tooling; justified suppressions keep the gate meaningful. |
| D-042 | Vulnerability reports go through GitHub private advisories (no personal e-mail address in the repository). | Keeps reporter data and embargoed details out of public channels. |
| D-043 | **Project files are SQLite databases** (`.roiproj`, format version 1) holding raw cells, import findings, the full change log, versions, acceptances and metadata. Saved atomically (temp file + rename, mode 0600); opened read-only with `trusted_schema=OFF`, `quick_check`, size limit and strict table/format checks; opening always assigns a fresh workspace id. | One portable, transactional file per client register that standard tools can inspect for audit, robust against crashes and safe to receive from third parties. |
| D-044 | Optional **projects folder** (`roi serve --projects DIR` / `ROI_PROJECTS_DIR`): every workspace is autosaved after each change and listed on the home page. Intended for single-user local mode – the folder is visible to every session of that instance; off by default. | Lets a consultant keep several client registers without manual saving, without weakening isolation in the default/shared mode. |
| D-045 | **Spreadsheets are read with python-calamine and written with XlsxWriter**; openpyxl (and defusedxml) are test-only dependencies now. | Profiling a 10 000-contract register: openpyxl took ~7 s to read and ~7 s to write; calamine reads in ~0.5 s and XlsxWriter writes in ~3 s. Calamine's XML parser rejects DTDs/entities, which removes the XXE class instead of relying on defusedxml being installed; XlsxWriter's in-memory mode leaves no temporary files with client data and `write_string` never creates formulas. Integral numbers are normalised to `int` (calamine reports floats) so imports behave exactly as before. |
| D-046 | The workbench's workspace store is bounded by a **row budget** (`ROI_MAX_STORE_ROWS`, default 500 000) in addition to the count limit; the newest workspace is always kept. | A 10 000-contract workspace needs ~215 MB; a count limit alone could let 20 such registers exhaust a small server. Rows are a cheap, good proxy for memory. Users who need to keep many large registers should enable the projects folder (autosave). |
| D-047 | **PDF reports are rendered from the reports' own HTML with WeasyPrint**, using one print stylesheet (`@page` A4, page numbers, light colours, repeated table headers, expanded details, no scripts) that also governs the browser's *Print → Save as PDF*. WeasyPrint is an optional extra (`[pdf]`) and part of the Docker image; without it the UI hides the PDF buttons and points to browser printing. Charts carry presentation attributes so they keep their colours outside the browser. The PDF caps long tables (top 50 provider groups, first 1 000 findings) – the HTML and JSON keep everything. | One layout source for HTML, print and PDF instead of a second report engine; WeasyPrint is pure Python on top of Pango, needs no browser and renders offline. Pango is awkward on Windows, hence optional with a zero-install fallback. The URL fetcher refuses every resource so nothing in a report can trigger a network request or file read. |
| D-048 | The DORA programme modules (Art. 30 contracts, incidents, FINMA mapping, readiness) live in their own packages (`dora_roi.contracts`, …) and are **linked to the register by key, never copied**: an Art. 30 assessment is keyed by the B_02.01 arrangement reference (c0010) and reads providers, entities and functions from the register at evaluation time. | Provider names, criticality and call-off relationships change while a register is being fixed; a copy would silently go stale. The register shows the compliance status on B_02.01 rows because both are joined live. |
| D-049 | Subsequent arrangements (call-offs, B_02.01 c0020 = subsequent, c0030 = overarching reference) **inherit** unassessed Art. 30 items from their overarching arrangement unless the assessor switches inheritance off; inherited gaps are listed once in the remediation plan, at the master (escalated if a critical call-off relies on it), or under the call-off when the master does not carry that provision itself. | Call-offs under a master agreement normally rely on its terms; assessing every call-off would multiply work and findings for one clause. |
| D-050 | Remediation priority: missing provision on an arrangement supporting a critical or important function = **high**; partial there, or missing elsewhere = **medium**; partial elsewhere = **low**. Key provisions (★: subcontracting, data return, authority cooperation, termination, TLPT, audit rights, exit) sort first within a priority. Target dates: 90 / 180 / 365 days from the plan date. | A rule a Head of Third-Party Risk can explain in one sentence and challenge; Art. 30 has applied since 17 January 2025, so dates are counted from the plan, not from renewal. Contract end dates are shown to align negotiations. |
| D-051 | Contract **suggestions** are keyword/heuristic only (EN/DE regular expressions per concept, matched clause by clause, negation-aware), run locally, and are never saved without review: the form is pre-filled, a banner says "not saved yet", each item shows the matched passage, and the heuristic's proposal is stored as `suggested_status` next to the reviewer's decision. | Requirement: no external AI or network calls. Recording the proposal and the decision side by side gives an audit trail of where the reviewer overruled the tool. |
| D-052 | Contract documents: DOCX is parsed with the standard library (DTDs rejected, uncompressed size bounded); PDF uses the optional pure-Python `pypdf` (extra `contracts`, included in `web`); OCR is out of scope; documents are processed in memory and not stored. | No native dependencies in the Docker image; scanned contracts are rare for the recent agreements that matter most and OCR quality would undermine trust in the suggestions. |
| D-053 | Programme data (assessments, incidents) belongs to a workspace and, like the register, lives in memory; it is exported/imported as JSON (lossless, with history) and as Excel for work with a client. | Keeps D-023's privacy model; the consultant saves the files with the client deliverables. |
| D-054 | New feature routes are registered from separate modules (`web/contracts_routes.py`, …) through a small `Ui` context (render, workspace lookup, upload reading) instead of growing `create_app`. Report strings of the programme modules live in `dora_roi.i18n` (no web dependency) and are merged into the interface catalogue. | `app.py` stays readable; client reports (remediation plan, readiness report) are rendered in EN or DE from the CLI as well as the web app. |
| D-055 | Branch `contracts-incidents` is based on `claude/zealous-pascal-4ws44y` and its PR targets that branch (stacked PR), so the diff shows only the programme modules while the base work is reviewed in parallel. | The base branch is still in progress in another session; targeting `main` would mix both changes in one review. |
| D-056 | Incident classification is **derived, never stored**: the log keeps the questionnaire answers and timestamps; outcome, triggered thresholds and deadlines are recomputed on every view. The history records each change of outcome ("— → major") and report submissions. | A stored classification can disagree with the answers after an edit; recomputation cannot. The history still documents what was decided when, which supervisors ask for. |
| D-057 | **Three-valued classification**: every answer may be *unknown*; the outcome is evaluated with unknowns as "not met" and as "met" and is definitive only if both agree, otherwise *undetermined* with the open questions that could change it. An unresolved incident's duration runs until now and is not final. | Classification has to happen within hours, with incomplete facts; the tool must neither declare "not major" prematurely nor force guesses, and it should say which facts are still needed. |
| D-058 | Every materiality threshold and reporting time limit is a field of a frozen `Thresholds` dataclass and printed into the generated `docs/INCIDENT_CLASSIFICATION.md`. | The official texts could not be verified offline (A-INC-*); a correction must be a one-line, reviewable change that also updates the documentation. |
| D-059 | Deadlines: initial = min(classification + 4 h, awareness + 24 h); intermediate = initial *submission* + 72 h; final = intermediate submission + 1 month; deadlines after a report not yet submitted are shown as *projected*. Weekend/bank-holiday relief is **not** applied. Countdowns are rendered server-side and refreshed by ~20 lines of JavaScript every 30 s (and on tab focus), without an ARIA live region. | Conservative deadlines are safer than late reports. Announcing a countdown every 30 s would make the page unusable with a screen reader; the value is read when the user reaches it. |
| D-060 | Timestamps are stored in UTC; each incident log has a display time zone (default Europe/Berlin, selectable) used for form input and reports; if tz data is missing the app falls back to UTC (and `tzdata` is a dependency on Windows). | Incident clocks are legal deadlines – ambiguity about time zones is a real failure mode in multi-country groups. |
| D-061 | Recurring incidents are grouped by an explicit **recurrence key** ("same apparent root cause") entered by the user, not inferred from text or provider; within a key the largest set of non-major incidents inside a 6-month window is combined. | Root-cause equivalence is a judgement call; an explicit key makes it reviewable and avoids false grouping of unrelated outages of the same provider. |
| D-062 | The FINMA view is a **mapping with two coverage levels**: *by design* (does the RoI, the Art. 30 checklist or the incident log hold this kind of information?) and *in this register* (are the mapped fields filled for the applicable records – conditional columns such as RTO only for critical functions – and are the linked Art. 30 provisions assessed?). A design-"covered" requirement needs ≥ 95 % completeness to count as covered. | A Swiss Head of Third-Party Risk needs both answers: "can one dataset serve FINMA at all?" and "is our dataset good enough today?". Measuring only applicable records avoids penalising correct blanks. |
| D-063 | Swiss group entities are **not** added to the sample register; the FINMA view explains that the EU subsidiaries' arrangements are covered from the group's perspective and what to do to include the Swiss bank (FIN-OS-04). | Adding non-DORA entities to B_01.02 would contaminate the supervisory sample; flagging entities as out of DORA scope is a backlog item. |
| D-064 | **Readiness traffic lights** per pillar with explicit, documented thresholds (register: errors; contracts: high-priority gaps and share of critical arrangements assessed; incidents: overdue reports, unreported recurring series, pending reports, undetermined classifications; concentration: level of the key messages). Overall = worst DORA pillar; grey = nothing to assess; FINMA is informational and does not drive the overall status. | A CRO needs a status that can be traced back to facts in one sentence each; a weighted score would hide which pillar is the problem. Grey avoids showing "green" for an incident log nobody maintains. |
| D-065 | The programme reports (readiness, remediation plan, incident summary) are **print-optimised self-contained HTML** (A4 `@page`, page breaks, repeated table headers, no JavaScript); since the merge with the base branch they are also offered as **PDF through the base's WeasyPrint pipeline (D-047)** when the `pdf` extra is installed (`…/readiness.pdf`, `-o report.pdf`), with print CSS that avoids layout features WeasyPrint lacks (`min()` in grid tracks, inline flex). | One layout for screen, print and PDF; PDF stays optional like the base's other reports. |
| D-066 | The overview page shows the readiness traffic lights as a teaser and links to the dashboard; the RoI stepper is unchanged. | Keeps the existing *Import → Fix → Analyse → Export* flow intact for users who only maintain the register, while making the programme visible from the first screen. |
| D-067 | The coverage gate is raised from 85 % to 90 % (`make cov`, CI). | The requested quality bar; actual coverage is ~98 %. |
| D-068 | Programme data is stored in project files as an **optional `programme` table** (key → JSON document in the module's own schema: `contracts`, `incidents`), validated with the same Pydantic models on load; the format version stays 1. | Files written before stay readable (the table is optional) and files written now still open in base-branch builds (extra tables are tolerated); tampered JSON is rejected like any other invalid project content. |
| D-069 | Every programme mutation (assessment saved/deleted/imported, incident created/changed/reported/resolved, time zone) appends a `Change` of kind `art30` / `incident` to the workspace's audit trail and triggers autosave; mutations run under the workspace lock. Register reconstruction (`raw_at`) ignores these entries. | One audit trail for everything an auditor may ask about, and no lost work with the projects folder enabled. |
| D-070 | The Art. 30 portfolio is **cached on the workspace** and invalidated by register edits and programme changes. | ~1.2 s per evaluation at 10 000 contracts; several screens (contracts, register, overview, dashboard, FINMA) need it per request. |
| D-071 | **Time-bound exceptions** for missing/partial provisions: reason (incl. compensating controls), approver and an end date are mandatory. A valid exception does not make the clause present – status *Gaps under exception*, counts stay truthful – but removes the gap from the action list and lists it under *Approved exceptions*; after the end date it is an open gap again. | DORA's Art. 30 provisions are mandatory, so "accepting" a gap must not look like compliance; but renegotiations with large providers take until renewal, and the plan must separate decided, time-boxed situations from unmanaged gaps. |
| D-072 | Readiness: the **concentration** light is computed from concentration metrics (group spend share, groups supporting ≥ 5 critical functions, single hard-to-substitute providers, exit-plan coverage, third-country groups, hidden concentration); **contract lifecycle** signals (expiries, notice deadlines) belong to the contracts pillar, which also flags arrangements with open Art. 30 gaps whose notice deadline falls within 180 days ("renegotiate now"). All readiness texts are generated from translated templates rather than the English key messages. | A red concentration light caused by an expiring contract sends a CRO to the wrong place; the renewal is the moment to close contract gaps. |
